JWT Architecture

CyberCore uses a dual-token strategy: a short-lived access token for regular API calls, and a long-lived refresh token that issues new access tokens transparently.

TokenLifetimeCookie nameCookie pathPurpose
Access token 15 min (configurable) access_token / Sent on every request; proves identity
Refresh token 7 days (configurable) refresh_token /users/refresh Issued new access tokens; path-restricted

Algorithm: HS256 (HMAC-SHA256). The secret is loaded from JWT_SECRET_KEY — minimum 32 characters, enforced at startup.

JWT Payload

{
  "sub":  "user-uuid-here",
  "type": "access",          // "access" | "refresh"
  "jti":  "random-uuid",     // JWT ID — used for revocation
  "iat":  1715000000,         // issued at (Unix timestamp)
  "exp":  1715000900          // expiry (Unix timestamp)
}

The jti field is a random UUID assigned at issue time. All required claims (sub, exp, iat, jti, type) are validated on every decode; missing claims raise 401.

AutoRefreshMiddleware

Registered on auth-service. Before every non-public request:

  1. If the access token is valid → pass through.
  2. If expired → check the refresh token (browser sends it because path matches).
  3. If refresh token is valid → issue a new access token, inject it into the request scope (so the route handler sees it), and set it in the response cookie.
  4. If no valid refresh token → pass through (route handler returns 401).

This means clients never have to implement token refresh logic. Sessions last until the refresh token expires (7 days) or the user explicitly logs out.

Secure flag in development

The Secure flag means cookies won't be sent over plain HTTP. In local development without TLS, you may need to set up a local HTTPS proxy (e.g. mkcert) or temporarily disable the Secure flag via env var.

Token Blacklist (Redis)

When a user logs out (or their account is deleted), both token JTIs are blacklisted immediately. Future requests with those tokens are rejected even before the tokens naturally expire.

Storage

Redis DB 1 (separate from Celery on DB 0)
Key:   auth:bl:{jti}
Value: "1"
TTL:   seconds until the token's natural expiry (exp - now)

Redis automatically deletes the key when TTL expires — no cleanup job needed.

Fallback behaviour

If Redis is unavailable, the blacklist falls back to an in-memory dict (original behaviour). Revocations are honoured within the current process lifetime but lost on restart. A warning is logged so operators know to fix the Redis connection.

Checking a token

def is_blacklisted(jti: str) -> bool:
    r = _get_redis()
    if r is not None:
        return bool(r.exists(f"auth:bl:{jti}"))
    return _fb_has(jti)   # in-memory fallback

Brute-Force Protection

The login endpoint tracks failed attempts per user in the database:

  • Every wrong password increments users.failed_login_attempts
  • After 5 failures, locked_until is set to now + 15 minutes
  • During lockout, all login attempts return 401 with a generic message
  • Successful login resets failed_login_attempts = 0 and locked_until = null

Error messages are kept intentionally generic ("Invalid email or password") to prevent user enumeration.

Per-user lockout

Lockout is per user (not per IP), so an attacker can't DoS another user from unlimited IPs. IP-based rate limiting should be added at the reverse proxy / CDN layer for production deployments.

RBAC — Roles & Privileges

Access control in organization-service uses a two-level model:

  1. Role — named group of privileges (e.g. "Developer", "Security Lead")
  2. Privilege — named permission string (e.g. scans.run)

Privilege strings used by scan-service

PrivilegeRequired for
scans.runSubmit new scans (git or upload)
scans.viewList scans, view scan details, list findings
scans.manageCancel and delete scans

Enforcement

Each protected route declares its required privilege via the require_org_privilege FastAPI dependency:

@router.post("/organizations/{slug}/scans/git")
async def submit_git_scan(
    slug: str,
    _priv: None = require_org_privilege("scans.run"),  # ← enforced here
):
    ...

The dependency fetches the user's privilege set from org-service (or from the 10s TTL cache) and raises 403 if the required privilege is absent. Users with no membership in the org get 403, not 404 — the org's existence is not leaked.

Git URL Validation — RCE Prevention

The worker runs git clone with user-supplied URLs. Without validation, this is a remote code execution vector — git supports dangerous transports like ext:: which execute arbitrary commands.

Validation rules

CheckPrevents
Must be a stringType confusion
Must not be emptyNull input
Must not start with -URL parsed as git option (--upload-pack=cmd)
No whitespace or control chars (ord < 0x20)Argument injection
Scheme must be http, https, or gitBlocks ext::, file://, ssh://, scp-style
Hostname must match ^[A-Za-z0-9.\-]{1,255}$IP literals, encoded chars, null bytes

Clone command

subprocess.run([
    "git", "clone",
    "--depth", "1",
    "--single-branch",
    "--",          # ← separates options from positional args
    safe_url,      # ← already validated
    str(dest),
], env={**os.environ, "GIT_TERMINAL_PROMPT": "0"}, ...)

The -- separator ensures that even a bypassed URL validator cannot turn the URL into a git flag. GIT_TERMINAL_PROMPT=0 prevents the worker from blocking indefinitely waiting for credentials on a private repo.

ZIP Security

Zip-slip (path traversal)

A malicious ZIP can contain entries with paths like ../../etc/passwd that escape the extraction directory. CyberCore defends at two layers:

  1. String check: Reject entries starting with / or \, or containing .. parts. Cheap O(1) pre-filter.
  2. Path resolution check: Resolve the full target path and call target.relative_to(dest_resolved). If the resolved path escapes the extraction root, raise RuntimeError.
target = (dest / info.filename).resolve()
try:
    target.relative_to(dest_resolved)
except ValueError:
    raise RuntimeError(f"ZIP rejected: entry escapes target '{info.filename}'")

Zip-bomb (decompression bomb)

A ZIP may contain 1 MB of data that decompresses to 100 GB. CyberCore enforces two limits before extracting:

  • Entry count: max 200,000 entries (configurable via SCAN_ZIP_MAX_ENTRIES)
  • Total uncompressed size: max 5 GiB (configurable via SCAN_ZIP_MAX_UNCOMPRESSED_BYTES)

Both are checked by iterating ZipFile.infolist() before any extraction happens. Extraction only starts if both checks pass.

Upload Limits

File uploads (ZIP archives) are read in 1 MiB chunks. A running byte counter is checked after each chunk:

while True:
    chunk = await file.read(1 * 1024 * 1024)  # 1 MiB chunks
    if not chunk:
        break
    written += len(chunk)
    if written > MAX_UPLOAD_BYTES:             # default 500 MiB
        # delete partial file, raise 413
        ...

This prevents a client from filling disk by sending more bytes than declared in Content-Length, and avoids loading the entire file into memory before the size check runs.

Password Policy

Validated at registration and password reset. A password is accepted only if it:

  • Is at least 12 characters long
  • Contains at least one uppercase letter
  • Contains at least one lowercase letter
  • Contains at least one digit
  • Contains at least one special character
  • Does not contain the user's full name or email

Passwords are hashed with bcrypt before storage. The plaintext is never logged or stored.

Email Tokens (Verification & Password Reset)

Tokens sent in emails are generated with secrets.token_urlsafe(48) (48 bytes → 64 URL-safe characters). Only the SHA-256 hash is stored in the database — the plaintext is never persisted.

When a new token is generated for a user, all previous unused tokens of the same type are invalidated (DELETE WHERE user_id = ? AND token_type = ? AND used_at IS NULL). This prevents token hoarding.

Auth Cache Trade-offs

The scan-service caches identity and privilege lookups for 10 seconds to reduce inter-service traffic. This introduces a staleness window:

CacheTTLStaleness scenario
User identity (user_cache) 10 s User logged out — scan-service may accept requests for up to 10 s
Privileges (priv_cache) 10 s Role revoked — user retains access for up to 10 s
Slug→UUID (org_id_cache) 300 s Org slug changed (rare) — old slug accepted for up to 5 min

These windows are intentionally short. The auth-service itself has no cache — the access token is validated cryptographically on every call. The 10-second window primarily protects against the dashboard's 3-second polling while a scan is active.

To change TTLs, set the corresponding env vars: SCAN_USER_CACHE_TTL_SECONDS, SCAN_PRIV_CACHE_TTL_SECONDS, SCAN_ORG_ID_CACHE_TTL_SECONDS.
