Architecture

CyberCore is a microservices platform. Each service owns its own database tables, communicates via HTTP, and can be deployed independently. This page explains the boundaries, data flows, and key design decisions.

Service Boundaries

auth-service

Sole owner of user identity. No other service writes to the users or user_tokens tables. Other services call auth-service to validate cookies and get the current user's UUID.

  • Issues JWT access tokens (15 min) and refresh tokens (7 days) as httpOnly cookies
  • AutoRefreshMiddleware silently renews the access token on every request when it's expired
  • Token revocation stored in Redis DB 1 with TTL — survives service restarts
  • Brute-force protection: 5 failed attempts → 15-minute lockout

organization-service

Multi-tenant boundary. Owns orgs, roles, privileges, and memberships. All role checks in other services go through this service's /roles/{slug}/my-privileges endpoint.

  • RBAC: each org has custom roles; each role has a set of named privileges
  • The creator of an org becomes its Owner (all privileges)
  • Two-step ownership transfer: owner initiates → email link → recipient accepts
  • Soft deletes on orgs (restored via /reactivate)

scan-service

Orchestrates scan jobs. Accepts submissions, enforces quotas, dispatches Celery tasks, and serves results. Does not run any scanning tools itself.

  • Validates user identity by forwarding cookies to auth-service
  • Validates privileges by calling org-service
  • Both calls are TTL-cached (10 s for identity/privileges, 5 min for slug→UUID)
  • Persists scan_jobs and scan_findings

scan-worker

A Celery worker process — no HTTP API. Picks tasks from the Redis queue, runs the security tools, deduplicates findings, and writes results back to MySQL.

Authenticated Request Lifecycle

Every protected API call on scan-service follows this path:

Client Request (with cookies)
        │
        ├─ 1. FastAPI dependency: get_current_user_id()
        │      └─ Checks user_cache (10s TTL, SHA-256 keyed on cookies)
        │         └─ Cache miss → POST auth-service/api/v1/users/me
        │            └─ Returns user_id (UUID)
        │
        ├─ 2. FastAPI dependency: require_org_privilege("scans.run")
        │      └─ Checks priv_cache (10s TTL, keyed on (cookie_hash, slug))
        │         └─ Cache miss → GET org-service/.../my-privileges
        │            └─ Returns frozenset of privilege strings
        │
        ├─ 3. Route resolves org slug → org UUID
        │      └─ Checks org_id_cache (5 min TTL, keyed on slug)
        │         └─ Cache miss → GET org-service/organizations/{slug}
        │
        └─ 4. Business logic runs (ScanService method)

Scan Pipeline

From "Submit" click to findings in the database:

scan-service: POST /scans/git
        │
        ├─ Enforce quota (single DB query — active + daily counts)
        ├─ Create ScanJob row  (status = "queued")
        ├─ celery.send_task("run_sast_scan", args=[job_id])
        │       → Redis queue
        └─ Return job (202 Accepted)

scan-worker: picks up task from Redis
        │
        ├─ Load job from DB; flip status → "running"
        │
        ├─ Prepare source:
        │   ├─ git_url → clone_repo()  (validate URL, shallow clone, --no-creds)
        │   └─ upload  → extract_zip() (zip-slip + zip-bomb checks)
        │
        ├─ Detect project type (single os.walk pass):
        │   ├─ .py/.pyw  → has_python
        │   ├─ .go       → has_go
        │   ├─ .js/.ts   → has_js_ts
        │   ├─ package.json  → has_pkg_json
        │   └─ pyproject/requirements → has_py_deps
        │
        ├─ Run tools (all applicable, errors are non-fatal):
        │   ├─ Always:     Bandit, Semgrep, Gitleaks, Trivy, Hadolint
        │   ├─ If py_deps: pip-audit
        │   ├─ If pkg_json: npm audit
        │   └─ If has_go:  gosec
        │
        ├─ Dedup findings by SHA-256 fingerprint
        │
        ├─ Bulk-insert findings (SQLAlchemy 2.0 Core, 500-row chunks)
        │
        ├─ Update job: status → "completed", findings_count
        │
        └─ Cleanup workspace directory

Authentication Flow

POST /users/login
        │
        ├─ Verify email + password (bcrypt)
        ├─ Create access_token  (JWT HS256, 15 min)
        ├─ Create refresh_token (JWT HS256, 7 days)
        └─ Set both as httpOnly cookies:
             access_token  — path="/",               max_age=900
             refresh_token — path="/users/refresh",  max_age=604800

Every subsequent request:
        │
        AutoRefreshMiddleware (auth-service only)
        ├─ Access token valid? → pass through
        └─ Access token expired?
              ├─ Refresh token valid? → issue new access_token cookie → continue
              └─ No valid refresh token → 401 (endpoint handles it)

POST /users/logout
        │
        ├─ Read both tokens from cookies
        ├─ Blacklist their JTIs in Redis (SETEX with remaining TTL)
        └─ Delete cookies from browser

Key Design Decisions

No shared database

Each service has its own logical database area. There are no cross-service foreign keys. Referential integrity at service boundaries is enforced by business logic, not DB constraints. This keeps services independently deployable and allows per-service database migrations.

JWT cookies instead of Authorization header

Tokens live in httpOnly cookies. JavaScript cannot read them, eliminating XSS-based token theft. The Secure and SameSite=Lax flags prevent cross-site transmission. The refresh token's path="/users/refresh" restriction means it is sent only to the refresh endpoint — even if the access token is stolen, the refresh token stays hidden.

TTL cache in scan-service

The dashboard polls /scans/{job_id} every few seconds while a scan runs. Without caching, each poll would trigger two inter-service HTTP calls. A 10-second in-process TTL cache eliminates >98% of those calls during active polling, at the cost of up to 10 s of staleness after a role/logout change — acceptable for this use case.

Celery for SAST execution

SAST scans can take minutes. Running them synchronously in the API process would block the event loop and risk timeouts. Celery decouples execution: the API returns immediately with a job ID, the worker runs the tools in the background, and the client polls for results. The worker has a 30-minute hard kill limit (time_limit=1800) and a 29-minute soft limit for graceful cleanup.

Single-pass extension detection

Before running tools, the worker detects which languages are present. The naive approach is one rglob("*.py") per extension — on a large repo, that's multiple full directory traversals. Instead, a single os.walk pass collects all extensions at once and early-exits as soon as all targets are found. Skips node_modules, .git, __pycache__, and other noise directories.

Bulk insert for findings

A scan may produce thousands of findings. Inserting them row-by-row with SQLAlchemy ORM objects is slow. Instead, the worker uses SQLAlchemy 2.0 Core insert() with executemany, chunked at 500 rows per batch. This lets the DB driver batch them into a single round-trip per chunk, cutting insert time dramatically.
