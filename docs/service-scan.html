Scan Service

FastAPI MySQL Celery / Redis Port :8082

The scan-service is the API layer for all security scanning operations. It accepts scan requests, enforces quotas, dispatches async tasks to the scan-worker, and serves the results. The service itself runs no scanning tools.

Quota Enforcement

Every scan submission checks two limits against the submitting organization:

  • Active limit: max 3 concurrent scans in queued or running state
  • Daily limit: max 3 scans submitted in the last 24 hours

Both limits are enforced in a single SQL query using conditional aggregation — no second round-trip:

active_count, daily_count = db.query(
    func.coalesce(func.sum(
        case((ScanJob.status.in_(("queued", "running")), 1), else_=0)
    ), 0),
    func.coalesce(func.sum(
        case((ScanJob.created_at >= since, 1), else_=0)
    ), 0),
).filter(
    ScanJob.organization_id == organization_id,
    ScanJob.deleted_at.is_(None),
).one()

Limits are configurable via env vars: SCAN_FREE_PLAN_ACTIVE_LIMIT and SCAN_FREE_PLAN_DAILY_LIMIT.

Git Scan Submission

The request body is validated before the job is created:

POST /api/v1/scans/organizations/{slug}/scans/git
{
  "name": "My Application v2.1",
  "target_url": "https://github.com/owner/my-app"
}

The target_url field validator enforces:

  • Scheme must be http, https, or git
  • No leading dash (prevents git CLI option injection)
  • No whitespace or control characters
  • Hostname must match [A-Za-z0-9.\-]{1,255}

On success returns 202 Accepted with the job object.

Upload Scan Submission

Accepts a multipart form upload:

curl -X POST \
  http://localhost:8082/api/v1/scans/organizations/my-org/scans/upload \
  -b cookies.txt \
  -F "name=My App Scan" \
  -F "file=@/path/to/code.zip;type=application/zip"
  • Only .zip files accepted (filename check)
  • Streamed in 1 MiB chunks — never fully loaded into memory
  • Rejected if total bytes exceed SCAN_UPLOAD_MAX_BYTES (default 500 MiB)
  • Empty uploads rejected (0-byte file)
  • ZIP is stored in SCAN_UPLOAD_DIR and passed to the worker via the DB row
  • Deleted from disk when the job is deleted or after worker extracts it

Findings Structure

The GET /findings endpoint returns paginated findings with severity counts:

{
  "total": 47,
  "truncated": false,
  "severity_counts": {
    "critical": 2,
    "high": 8,
    "medium": 15,
    "low": 20,
    "info": 2
  },
  "items": [
    {
      "id": "uuid",
      "tool": "semgrep",
      "rule_id": "python.django.security.injection.tainted-sql-string",
      "severity": "high",
      "confidence": "high",
      "title": "SQL injection via string formatting",
      "message": "User input is formatted into a SQL query...",
      "file_path": "app/views.py",
      "line_start": 42,
      "line_end": 44,
      "code_snippet": "query = f\"SELECT * FROM users WHERE id = {user_id}\"",
      "cwe": "CWE-89",
      "owasp": "A03:2021",
      "fingerprint": "sha256hex...",
      "created_at": "2026-05-14T10:00:00Z"
    }
  ]
}

Pagination parameters: offset (default 0), limit (default 100, max 500). The truncated field is true when offset + len(items) < total.

Filters: ?severity=high, ?tool=semgrep. Severity counts always reflect the full scan, not the filtered set, so the summary bar stays accurate.

Inter-service Caching

The scan-service caches results of cross-service calls in a process-local TTL+LRU cache. This is critical for performance: the dashboard polls scan status every 3 seconds while a scan is active.

CacheKeyTTLEliminates
user_cache SHA-256(cookies) 10 s Repeated GET /users/me to auth-service
priv_cache (SHA-256(cookies), slug) 10 s Repeated GET /roles/{slug}/my-privileges to org-service
org_id_cache slug string 300 s Repeated GET /organizations/{slug} to org-service

The cache key for user/privilege lookups is a SHA-256 hash of the cookie header — raw tokens are never stored in memory. Multiple Uvicorn workers each maintain their own copy (process-local), which is fine because TTLs are short.

Cancel & Delete

Cancel

Allowed only for queued or running jobs. Revokes the Celery task and sets status to cancelled. If the worker has already started, it detects the revocation signal and stops.

Delete (soft)

Sets deleted_at = now(). The job and its findings are hidden from all list and detail endpoints but remain in the database. Additional behaviour:

  • If status is running → returns 400. Cancel first, then delete.
  • If status is queued → auto-cancels (revokes Celery task, status → cancelled) before soft-deleting.
  • If target_type = "upload" → deletes the ZIP file from disk (best-effort).

All findings with scan_job_id matching a soft-deleted job remain in the database (useful for audits). They are cascade-deleted only if the job row is hard-deleted from the DB directly.
