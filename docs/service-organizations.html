Core Concepts

Organization

The top-level multi-tenant boundary. Every scan, log project, and alert is scoped to an organization. An org has:

  • A unique slug (URL-friendly, e.g. my-company)
  • A human-readable name
  • One Owner (the creator; can be transferred)
  • Zero or more Members, each assigned a Role
  • Zero or more custom Roles, each with a set of Privileges

Slug

The slug appears in every API URL that is org-scoped: /api/v1/scans/organizations/my-company/scans. Slugs must be globally unique, URL-safe, and lowercase. When an org is soft-deleted, its slug is freed for others to claim.

Owner

The Owner is a special built-in role with all privileges. There is always exactly one Owner per org. The Owner cannot be removed by regular role assignment — ownership must be transferred explicitly via the two-step transfer flow.

Privilege System

Privileges are named strings that represent specific actions. They are grouped into categories for the UI. Each service defines which privileges it checks.

Current privilege strings

PrivilegeChecked byAllows
scans.runscan-serviceSubmit new scans
scans.viewscan-serviceView scan list, details, and findings
scans.managescan-serviceCancel and delete scans
members.vieworg-serviceList org members
members.inviteorg-serviceInvite new members
members.removeorg-serviceRemove members
roles.vieworg-serviceList roles and their privileges
roles.manageorg-serviceCreate, edit, delete custom roles
org.settingsorg-serviceUpdate org name, slug, settings

Checking privileges from another service

# Get the set of privileges the current user holds in org "my-company"
GET /api/v1/organizations/roles/my-company/my-privileges

# Response:
{
  "privileges": ["scans.run", "scans.view", "scans.manage", "members.view"]
}

This endpoint is called by scan-service on every protected request (with a 10-second TTL cache). An empty privilege set means the user is not a member of the org — return 403, not 404.

Custom Roles

Org admins can create roles beyond the built-in Owner role. A role has:

  • name — displayed in the UI
  • description — optional human-readable explanation
  • color — hex color for the UI badge
  • privileges — the set of privilege strings this role grants

Example: Creating a "Security Analyst" role

POST /api/v1/organizations/roles/my-company
{
  "name": "Security Analyst",
  "description": "Can run and view scans but cannot manage them",
  "color": "#3fb950",
  "privileges": ["scans.run", "scans.view", "members.view"]
}

The creator must hold roles.manage privilege in the org. Roles require roles.view to list. Roles cannot be assigned privileges the creator doesn't themselves hold (privilege escalation prevention).

Membership

Members are users (identified by UUID from auth-service) associated with an org via a role. A user can be a member of multiple orgs with different roles.

Invite flow

  1. Actor with members.invite calls POST /organizations/{slug}/members/invite with the invitee's email and the role to assign.
  2. An email with an invite link is sent to the invitee.
  3. The invitee accepts via POST /invites/accept with the token from the email.
  4. If the invitee has no account, they are prompted to register first.

Removing a member

Requires members.remove privilege. Owners cannot be removed via the member endpoint — transfer ownership first.

Ownership Transfer

A two-step process to prevent accidental ownership loss:

1

Owner initiates transfer

PATCH /api/v1/organizations/my-company/transfer-ownership
{ "new_owner_id": "uuid-of-recipient" }

The recipient must already be a member of the org. An email with an acceptance link is sent. The current owner retains ownership until the recipient accepts.

2

Recipient accepts

POST /api/v1/organizations/transfer-ownership/accept
{ "token": "TOKEN_FROM_EMAIL" }

The token is single-use and expires. If it expires, the current owner must initiate again. Upon acceptance, the previous owner's role is changed to a regular member role.

Soft Delete & Reactivation

Deleting an org sets deleted_at = now() and frees the slug. The org's data (scan history, member list) is preserved. Only the Owner can delete their org.

Reactivation

POST /api/v1/organizations/{org_id}/reactivate
{ "new_slug": "my-company-v2" }   # optional: only needed if original slug was taken

Only the original Owner can reactivate. If the original slug is still available, new_slug is optional. If taken, a new slug must be provided (returns 409 if the new slug is also taken).

Inter-service Usage

Other services interact with org-service in two ways:

1. Get org UUID from slug

GET /api/v1/organizations/{slug}
# Returns the full org object including the UUID (id field)
# Used by scan-service to resolve slug → UUID for the scan_jobs.organization_id column

2. Check user's privileges

GET /api/v1/organizations/roles/{slug}/my-privileges
# Returns { "privileges": ["scans.run", ...] }
# Cookies forwarded from the original user request
# Called by scan-service before every protected action
Forward cookies, not tokens

Services forward the user's original cookies when calling org-service and auth-service. They do not extract the JWT, decode it, and re-authenticate — the cookie is the credential. This keeps the auth surface narrow: only auth-service validates JWTs.
