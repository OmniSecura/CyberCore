Docker & Deployment

Docker Compose MySQL 8.0 Redis 7 nginx 1.27

CyberCore ships with a single docker-compose.yml at the repository root that starts every service — database, cache, backend microservices, SAST worker, and the React dashboard — with one command.

Container Overview

Service name Image / build Host port Role
db mysql:8.0 3306 Relational database — three schemas: auth_db, org_db, scan_db
redis redis:7-alpine 6379 Celery broker + result backend (DB 0) & token blacklist (DB 1)
auth ./services/auth-service 8000 JWT auth — registration, login, MFA, token refresh, email flows
org ./services/organization-service 8081 Organization management, RBAC roles, member invitations
scan ./services/scan-service 8082 Scan orchestrator — submits jobs to Celery, returns results
worker ./workers/scan-worker — Celery worker — runs SAST tools (Bandit, Semgrep, Gitleaks, Trivy…)
dashboard ./dashboard 80 React SPA built by Vite, served by nginx which also proxies /api/*

Quick Start

1

Clone the repository

git clone https://github.com/YOUR_USERNAME/cybercore.git
cd cybercore
2

Create your .env file

cp .env.example .env

Open .env and set at minimum:

  • MYSQL_ROOT_PASSWORD — any strong password
  • MYSQL_PASSWORD — the app-user password
  • JWT_SECRET_KEY — a long random string (see below)
# Generate a secure JWT secret:
python -c "import secrets; print(secrets.token_hex(64))"
3

Build & start everything

docker compose up --build -d

On first run Docker will:

  • Pull MySQL 8.0 and Redis 7 images
  • Build all four Python service images (auth, org, scan, worker)
  • Build the dashboard (Node 20 → Vite build → nginx)
  • Run database/docker-init/01_databases.sql to create the three schemas
  • Let each service create its own tables via SQLAlchemy (DB_CREATE_TABLES=true)
4

Open the app

Navigate to http://localhost — the dashboard is live. Register your first user, verify the email (check the auth service logs if no mail server is configured — the token is logged), and you're in.

Environment Variables

All variables are set in the root .env file. The compose file reads them with ${VAR:-default} syntax so defaults work even without .env (useful for CI).

VariableDefaultUsed byNotes
MYSQL_ROOT_PASSWORD changeme_root db MySQL root password — change in production
MYSQL_USER cybercore db, all services App-level DB user
MYSQL_PASSWORD changeme_app db, all services App-level DB password — change in production
JWT_SECRET_KEY required auth Signs all JWTs — minimum 64 hex chars; must stay secret
MAIL_SERVER — auth SMTP host (e.g. smtp.gmail.com)
MAIL_PORT 587 auth SMTP port
MAIL_USERNAME — auth SMTP login username
MAIL_PASSWORD — auth SMTP login password / app-password
MAIL_FROM noreply@cybercore.dev auth Sender address for all system emails
ALLOWED_ORIGINS http://localhost:80,
http://localhost:3000		 auth, org, scan Comma-separated CORS origins — add your production domain here
JWT_SECRET_KEY is required

The compose file uses ${JWT_SECRET_KEY:?...} — Docker will refuse to start if this variable is missing from .env. Generate one and set it before running docker compose up.

Networking

All containers share the cybercore_net bridge network and reach each other by service name:

dashboard ──→ http://auth:8000      (nginx proxy)
dashboard ──→ http://org:8081       (nginx proxy)
dashboard ──→ http://scan:8082      (nginx proxy)
scan      ──→ http://auth:8000      (token verification)
org       ──→ http://auth:8000      (token verification)
scan      ──→ redis:6379            (Celery broker/backend)
worker    ──→ redis:6379            (Celery broker/backend)
auth      ──→ redis:6379            (token blacklist, DB 1)
auth      ──→ db:3306               (auth_db)
org       ──→ db:3306               (org_db)
scan      ──→ db:3306               (scan_db)
worker    ──→ db:3306               (scan_db)

Host-side ports (3306, 6379, 8000–8082) are exposed for local developer tooling (DBeaver, RedisInsight, Swagger UI). In production you should remove those bindings and only expose port 80 (or 443) via the dashboard nginx.

Volumes

VolumeMounted inPurpose
mysql_data db → /var/lib/mysql Persists all database data across restarts
redis_data redis → /data Persists Celery results and token blacklist across restarts
scan_uploads scan + worker → /tmp/cybercore/uploads Shared volume for ZIP uploads — scan writes, worker reads
scan_workspace worker → /tmp/cybercore/scans Temporary scan directories (git clones, extracted ZIPs)
Shared upload volume

scan_uploads is mounted in both scan (writes the uploaded file) and worker (reads the file to extract and scan). Without this shared volume, the worker container would not have access to files uploaded through the scan-service API.

Building Images

Build all at once

docker compose build

Rebuild a single service after a code change

docker compose build auth
docker compose up -d auth   # restart only auth

Build arguments — pin tool versions in the worker

The scan-worker Dockerfile exposes ARG variables for each SAST binary so you can pin versions without editing the file:

docker compose build \
  --build-arg GITLEAKS_VERSION=8.18.4 \
  --build-arg TRIVY_VERSION=0.52.2 \
  --build-arg GOSEC_VERSION=2.21.4 \
  --build-arg HADOLINT_VERSION=2.12.0 \
  worker

Useful Commands

Logs

docker compose logs -f             # tail all services
docker compose logs -f auth        # tail auth-service only
docker compose logs -f worker      # tail scan-worker (Celery output)

Shell access

docker compose exec auth bash      # shell inside auth container
docker compose exec db mysql -u cybercore -p auth_db  # MySQL prompt

Stop / restart

docker compose down                # stop containers (data volumes preserved)
docker compose down -v             # stop AND delete all volumes (full reset)
docker compose restart auth        # restart a single service

View running containers & health

docker compose ps

Create a superadmin user

# Register via the API (any user), then promote via MySQL:
docker compose exec db mysql -u cybercore -p auth_db \
  -e "UPDATE users SET is_superadmin=1 WHERE email='your@email.com';"

Dashboard & nginx

The dashboard container is a two-stage build:

1

Build stage (Node 20 Alpine)

Runs npm ci && npm run build. The Vite output lands in /app/dist.

2

Runtime stage (nginx 1.27 Alpine)

Copies /app/dist into /usr/share/nginx/html. The custom nginx.conf handles two jobs:

  • SPA routing — all unknown paths return index.html so React Router can take over
  • API proxy — /api/v1/* paths are forwarded to the correct backend service by name

nginx proxy rules (mirrors vite.config.js)

/api/v1/inviteshttp://org:8081
/api/v1/organizationshttp://org:8081
/api/v1/usershttp://auth:8000

Production Notes

Change the defaults before going live
  • Set strong, unique values for MYSQL_ROOT_PASSWORD, MYSQL_PASSWORD, and JWT_SECRET_KEY in .env.
  • Never commit .env to git — it is already in .gitignore.

HTTPS / TLS

In production, place a reverse proxy (Caddy, nginx, Traefik) in front of the dashboard container that terminates TLS. Update ALLOWED_ORIGINS to your https:// domain:

ALLOWED_ORIGINS=https://app.cybercore.dev

Remove developer-facing port bindings

The compose file exposes MySQL (3306), Redis (6379), and the individual service ports (8000–8082) for local dev convenience. In production, remove those ports: entries — only expose port 80 (or 443 via your TLS proxy) so the internal services are unreachable from the internet.

Resource limits

The scan-worker downloads git repos and runs multiple SAST tools concurrently. In production, add deploy.resources.limits to the worker service in docker-compose.yml:

worker:
  deploy:
    resources:
      limits:
        cpus: "2.0"
        memory: 4G

Worker concurrency

The default Celery concurrency is 2 (two parallel scan tasks). Increase it for machines with more cores by overriding the CMD in docker-compose.yml or by passing a build arg / env var:

worker:
  environment:
    CELERY_CONCURRENCY: "4"   # if the worker reads this var

Or override the command directly:

worker:
  command: >
    python -m celery -A src.celery_app:celery_app worker
    --loglevel=INFO --queues=sast --concurrency=4
