DAST Worker

Celery Redis OWASP ZAP Queue: dast

The dast-worker is a Celery process that runs Dynamic Application Security Testing scans against live web applications. Unlike SAST, which analyses source code at rest, DAST drives the OWASP ZAP proxy/scanner over its REST API to crawl, fingerprint, and attack a running target.

Architecture

The DAST pipeline reuses the SAST scan-service and the shared scan_jobs / scan_findings tables. What differs is the queue (dast), the worker process, and the analysis engine (ZAP rather than Bandit/Semgrep/etc.).

Credentials never persist

When the user supplies a token, cookie, or login credentials, they travel through the Celery broker message in Redis — never to the database. After the worker ACKs the task the message is dropped from the broker. The visible extra.auth_type on the scan job is just a label for the UI.

Scan Profiles

ProfileWhat ZAP doesPayloads sent?RuntimeUse when
passive Discovery + passive analysis (headers, cookies, TLS, info disclosure) No 2 – 15 min First test on any target; safe even when ownership is uncertain
active Discovery + passive + real attack payloads (SQLi, XSS, command injection, SSRF, XXE, path traversal) Yes — real attacks 15 min – 1 h+ Only on apps you own. Will create test rows, may trigger destructive endpoints if not excluded.
Active scans are real attacks

An active scan sends payloads like ' OR 1=1 --, <script>alert(1)</script>, ; rm -rf / etc. to every parameter on every discovered endpoint. Only run them against targets you own or have explicit written permission to test.

Discovery Modes

Discovery is the phase that populates ZAP's site tree with endpoints to scan. You pick exactly one mode per job.

ModeHow it worksBest forCaveats
spider Classic HTTP crawler — fetches the target, follows <a> and <form> links. Server-rendered websites Cannot see JS-rendered routes (React/Vue/Angular).
ajax_spider Headless browser (HtmlUnit) walks the SPA, clicks elements, follows XHR. Single-page apps ~5× slower than spider; needs more time budget.
openapi ZAP imports an OpenAPI/Swagger spec from a URL, populates the site tree directly. REST APIs (FastAPI, Express, Flask-RESTX) Requires the spec to be reachable from the worker.

Authentication Modes

Without authentication, ZAP only sees public surface (login screen, marketing pages). Configuring auth dramatically increases scan coverage on real applications.

bearer — header injection

Adds Authorization: Bearer <token> to every outgoing ZAP request via the Replacer add-on. Works for any API that accepts a bearer header.

{
  "type": "bearer",
  "token": "eyJhbGciOiJIUzI1NiI..."
}

cookie — Cookie header injection

Adds a raw Cookie: ... header to every request. Designed for apps that use httpOnly session cookies (so JavaScript can't read them) — the user logs in via a normal browser, copies the cookie value from DevTools, and pastes it in.

{
  "type": "cookie",
  "cookie": "access_token=eyJ...; refresh_token=eyJ..."
}

form — form-encoded login

ZAP performs a classic application/x-www-form-urlencoded login itself and reuses the resulting session. Suitable for HTML forms.

{
  "type": "form",
  "login_url": "https://app.example.com/login",
  "username": "alice",
  "password": "s3cret",
  "username_field": "username",
  "password_field": "password"
}

json_form — JSON body login

For modern APIs (FastAPI, Express) whose login endpoint expects a JSON body rather than form-encoded data. The user supplies a free-form body template with the literal placeholders {%username%} and {%password%} that ZAP substitutes at runtime.

{
  "type": "json_form",
  "login_url": "http://api.example.com/v1/users/login",
  "username": "alice@example.com",
  "password": "s3cret",
  "body_template": "{\"email\":\"{%username%}\",\"password\":\"{%password%}\",\"remember_me\":true}"
}
Custom request bodies

The body_template field is intentionally free-form — your login endpoint can require any combination of extra fields (client IDs, device fingerprints, nested envelopes) and the template covers them all. The schema validator ensures the body is valid JSON and contains both placeholders before queuing the scan.

Credential cleanup

Whether the scan succeeds, fails, or is cancelled mid-run, the worker's finally block:

  • Removes the Replacer rule (bearer / cookie modes) so the next job doesn't inherit it.
  • Disables forced-user mode (form / json_form modes).
  • Deletes the ZAP context.

Exclude Paths

Paths or patterns the worker should keep out of scope. Critical for active scans: without exclusions, ZAP will happily POST attack payloads to /users/me DELETE, /admin/wipe-database, etc.

Three input forms are accepted:

InputExpanded regexUse
/logout https?://host\.com(:\d+)?/logout Exact path match
/admin/* https?://host\.com(:\d+)?/admin/.* Glob — shell-style wildcards
^.*\.json$ passed through verbatim Raw regex — anything not starting with /

Limits: max 20 entries per scan, 256 characters each. Invalid regex patterns are logged and skipped — they don't crash the scan.

Execution Pipeline

1. Load ScanJob from DB; flip status → "running"
     ├─ cancelled / soft-deleted → exit early
     └─ snapshot target_url, profile, discovery_mode, openapi_url,
        exclude_paths from job.extra

2. Read auth payload from Celery kwargs (NOT from job.extra)

3. Wait for ZAP daemon: poll /JSON/core/view/version/ up to 60 s

4. Create fresh ZAP context (job-):
     ├─ include regex: host pattern from target_url
     └─ exclude regex: one per exclude_paths entry

5. Configure auth BEFORE discovery:
     ├─ bearer    → Replacer rule on Authorization header
     ├─ cookie    → Replacer rule on Cookie header
     ├─ form      → formBasedAuthentication + user + forced-user mode
     └─ json_form → jsonBasedAuthentication + user + forced-user mode

6. Run discovery (one of):
     ├─ spider      → poll /JSON/spider/view/status/ to 100%
     ├─ ajax_spider → poll /JSON/ajaxSpider/view/status/ to "stopped"
     └─ openapi     → import via /JSON/openapi/action/importUrl/

7. Drain passive scanner:
     └─ poll /JSON/pscan/view/recordsToScan/ until 0

8. Optional active scan (profile=='active'):
     └─ poll /JSON/ascan/view/status/ to 100%

9. Collect alerts: paginated GET /JSON/core/view/alerts/, 200 per page

10. Parse alerts → ScanFinding dicts (zap_parser.py)

11. Deduplicate by fingerprint; bulk insert (500-row chunks)

12. Update job: status='completed', findings_count=N, completed_at=now()

13. Cleanup (always — even on failure):
     ├─ remove Replacer rules
     ├─ disable forced-user mode
     └─ remove ZAP context

Each long-running phase updates job.extra.progress and job.extra.current_phase every 5 seconds so the dashboard can show live progress.

Findings Format

ZAP alerts are normalised by zap_parser.py into the shared ScanFinding shape so the dashboard renders DAST and SAST results identically. DAST-specific mappings:

ScanFinding columnDAST value
tool'zap'
rule_idZAP plugin ID (e.g. 10021, 40018)
severityMapped from ZAP risk — high, medium, low, info (ZAP's "informational" → "info")
confidenceFrom ZAP confidence — user-confirmed/high → "high", medium → "medium", low/false-positive → "low"
file_pathThe URL of the affected endpoint (column reused from SAST)
line_start / line_endNULL (URLs have no lines)
code_snippetZAP evidence string — the request fragment that triggered the alert
messageDescription, method, parameter, attack payload, evidence, and suggested fix, joined with blank lines
cweNormalised as CWE-NNN
fingerprintSHA-256 of rule_id : url : param : evidence

Safeguards

URL validation (scan-service)

_ALLOWED_WEB_SCHEMES = ("http", "https")

# Private/loopback IPs literally written in the URL are rejected.
# 127.0.0.0/8, 10/8, 172.16/12, 192.168/16, 169.254/16 (link-local),
# multicast, reserved, unspecified, and the string "localhost".
if _is_private_or_local(host):
    raise ValueError("Cannot scan private, loopback, or link-local addresses.")

Hostnames (e.g. auth, dashboard) pass through — they are not IP literals. The worker reaches them over the internal cybercore_net Docker network.

Security headers across CyberCore services

Auth-service, organization-service, and scan-service all run a SecurityHeadersMiddleware that sets:

X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()

This closes the baseline findings ZAP would otherwise raise on every FastAPI response.

Starting the worker

The dast-worker container uses the same image as the SAST worker but is started with a different CMD:

python -m celery -A src.celery_app:celery_app worker \
  --loglevel=INFO \
  --queues=dast \
  --concurrency=1 \
  --hostname=dast-worker@%h

Why concurrency=1?

A single ZAP daemon shares state between scans — passive scanner queue, active scanner thread pool, alert store. Running two scans concurrently against the same daemon would mix progress and slow both down without freeing up resources. To scale horizontally, run multiple ZAP daemons each paired with one dast-worker.
