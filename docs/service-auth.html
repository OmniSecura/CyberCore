Auth Service

FastAPI MySQL Redis Port :8000

The auth-service is the sole identity provider for CyberCore. It handles user registration, login, email verification, password resets, JWT issuance, and session management. No other service writes user data.

user_tokens table

Stores hashed tokens for email verification, password reset, and org invites.

ColumnTypeNotes
idCHAR(36)UUID primary key
user_idCHAR(36)FK → users.id (CASCADE DELETE)
token_hashVARCHAR(255)SHA-256 of the plaintext token; UNIQUE
token_typeVARCHAR(50)email_verification | password_reset | org_invite
expires_atDATETIMEVerification: 24h. Password reset: 1h.
used_atDATETIMENULL = unused. Set when token is consumed.

Registration Flow

POST /api/v1/users/register
  {email, full_name, password}
        │
        ├─ Validate password policy (12+ chars, uppercase, lowercase, digit, special)
        ├─ Check email uniqueness
        ├─ Hash password with bcrypt
        ├─ INSERT user (email_verified=false)
        ├─ Generate email verification token (secrets.token_urlsafe(48))
        ├─ Store SHA-256(token) in user_tokens table (TTL 24h)
        ├─ Send welcome email (best-effort, non-blocking)
        ├─ Send verification email with token link (best-effort)
        └─ Return 201 { "message": "Account created..." }

        ⚠ No tokens issued. User must verify email before logging in.

Login & Session Flow

POST /api/v1/users/login
  {email, password}
        │
        ├─ Look up user by email
        ├─ Check: is_active, email_verified, locked_until
        ├─ Verify bcrypt(password, password_hash)
        │     └─ Failure: increment failed_login_attempts
        │          └─ ≥ 5 failures → set locked_until = now + 15 min
        ├─ Reset failed_login_attempts, update last_login_at
        ├─ create_access_token(user_id)   → JWT HS256, 15 min
        ├─ create_refresh_token(user_id)  → JWT HS256, 7 days
        └─ Set cookies:
             access_token  (path="/",              max_age=900,    httpOnly, Secure, SameSite=Lax)
             refresh_token (path="/users/refresh", max_age=604800, httpOnly, Secure, SameSite=Lax)
        └─ Return 200 { "message": "Login successful" }

Email Verification

GET /api/v1/email/verify?token=TOKEN
        │
        ├─ SHA-256 hash the plaintext token
        ├─ Find user_tokens record (hash match, type="email_verification", used_at=NULL, not expired)
        ├─ Mark token as used (used_at = now)
        ├─ Set user.email_verified = true
        └─ Return 200

Generating a new verification token via POST /api/v1/users/me/resend-verification invalidates all previous unused verification tokens for that user.

Password Reset

Step 1 — Request:
POST /api/v1/email/reset-password/request
  {email}
        │
        ├─ Look up user (silently succeed even if not found — prevents enumeration)
        ├─ Generate reset token (TTL 1h)
        ├─ Send reset email (best-effort)
        └─ Return 200 regardless

Step 2 — Confirm:
POST /api/v1/email/reset-password/confirm
  {token, new_password}
        │
        ├─ Look up token (hash match, type="password_reset", unused, not expired)
        ├─ Re-validate new_password against policy
        │     └─ Validation failure → restore token as unused (user can retry)
        ├─ Update password_hash
        └─ Return 200

Logout

POST /api/v1/users/logout
        │
        ├─ Read access_token cookie → extract (jti, exp)
        ├─ Read refresh_token cookie → extract (jti, exp)
        ├─ For each: Redis SETEX "auth:bl:{jti}" remaining_ttl "1"
        └─ Delete both cookies from browser (max_age=0)

After logout, any subsequent request with the old cookies will fail at is_blacklisted(jti) — even before the tokens naturally expire.

AutoRefreshMiddleware

Registered on the auth-service app. Intercepts every non-public request:

class AutoRefreshMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        if request.url.path in _PUBLIC_PATHS:
            return await call_next(request)

        # Access token still valid? Pass through.
        access_token = request.cookies.get("access_token")
        if access_token and self._is_valid_access_token(access_token):
            return await call_next(request)

        # Try refresh token
        refresh_token = request.cookies.get("refresh_token")
        user_id = self._validate_refresh_token(refresh_token)
        if not user_id:
            return await call_next(request)  # endpoint returns 401

        # Issue new access token, inject into request + response
        new_token = create_access_token(user_id)
        # ... inject into request scope ...
        response = await call_next(request)
        response.set_cookie("access_token", new_token, ...)
        return response

Public paths that bypass the middleware:

_PUBLIC_PATHS = {
    "/v1/users/login",
    "/v1/users/register",
    "/v1/users/refresh",
    "/v1/email/verify",
    "/v1/email/reset-password/request",
    "/v1/email/reset-password/confirm",
    "/health", "/docs", "/openapi.json", "/",
}

Superadmin

Users with is_superadmin = true bypass the regular privilege checks in org-service and can access admin endpoints like DELETE /users/admin/{user_id}. The flag is set directly in the database — there is no self-promotion endpoint.

UPDATE users SET is_superadmin = TRUE WHERE email = 'admin@yourcompany.com';
Superadmin is powerful

Keep the number of superadmins minimal. A superadmin can soft-delete any user without a password confirmation. Audit all superadmin actions in production.
